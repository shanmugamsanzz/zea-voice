# Post-call summary continuity

Task 6 reuses the existing summary queue and the unique `call_ai_summaries` record per call. It requires migration `1791373000000_conversation-summary-context.js` after Tasks 1–5. No new `.env` setting is required. Summarization still requires enabling Post-Call Summary on the agent and assigning a connected LLM and summary instructions; it is not enabled automatically for existing agents.

The built-in summary instructions request purpose, collected facts, missing information, unresolved questions, current status, agreed next action and explicit callback details. These continuity fields live in `collected_data`, alongside company-specific fields. The narrative summary includes those facts for next-call context. Existing summary/outcome/intent/sentiment/follow-up fields and older stored summaries remain compatible. Callback time wording is preserved as evidence; generating a summary does not create a scheduled callback or change a contact name.

A completed summary is joined to its conversation through the original call link. Runtime history reads completed summaries directly, in call chronology, using the configured count and character limit. There is no second copy of summary text to become stale. A database trigger updates the thread timestamp in the same transaction as summary completion and usage persistence. A late summary from an older call therefore cannot replace a newer call's summary as the latest context. Historical summaries become readable when Task 5 backfill links their calls.

Claiming a job creates a unique processing token. Active claims are not reclaimed before the provider timeout plus a 60-second recovery allowance. BullMQ uses that same lock duration for stalled recovery. Completion, failure and skip writes require the claimed token, protecting recovered jobs from a stale worker. Summary completion, its usage event and thread update commit together. Completed jobs remain final and are not summarized or billed again on duplicate delivery. External webhook delivery retains the existing behavior; this change does not promise exactly-once delivery to an external server.

Invalid output and retryable provider failures use the existing configured retry count and queue backoff. Exhausted failures remain visible as failed summaries. Empty final transcripts are skipped. Transcripts, recordings, call results and original call billing are never removed or replaced by summarization. If the next call arrives before its predecessor's summary finishes, only already completed summaries are included.

Run `npm run verify:conversation-summary-context` plus the existing post-call suites. Local fixtures cover claim exclusion, token fencing, transcript preservation, context fields and tenant-scoped trigger SQL. Actual PostgreSQL transactions, concurrent workers and Redis restart recovery still require staging verification before deployment.
