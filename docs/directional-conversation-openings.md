# Direction-specific runtime and contextual openings

Task 8 selects inbound/outbound prompts and welcomes using the actual persisted call direction, independently of Agent Usage. Both canonical runtime configuration and the runtime agent use that selection. Missing directional prompts fall back to the legacy prompt; a missing welcome field falls back to the legacy welcome, while an explicitly cleared nullable welcome remains cleared. Deploy the preceding migrations before restarting the backend.

First-time phone conversations use the selected welcome and its existing template support. Returning means a previous answered call in the contact's company thread; missed calls alone do not count. Completed summaries are loaded using the configured count and length budget. Returning callers receive a short LLM-generated opening; a persisted current-call purpose such as a reminder can also require one. A pending task alone is not treated as this call's scheduled purpose. Empty/unavailable summaries do not justify invented history.

The opening request uses the selected prompt, structured context and configured language, has no tools, and is limited to 160 output tokens and 400 characters. Inbound openings briefly acknowledge relevant history and invite continuation. Outbound follow-ups explain their actual purpose and ask whether now is convenient. The instructions require identity confirmation before revealing sensitive details. A stored phone/name does not establish identity. Generation/lookup failures fall back to the selected welcome. User-Initiates continues to listen without generating or speaking an opening. Browser tests use the direction prompt/welcome but do not look up phone contact history.

Returning-call context is also available in the continuing system prompt, bounded by the existing overall prompt limit. If that limit leaves no room, the configured prompt remains authoritative and the opening request still receives its bounded context. Caller-specific openings are not read from or written to the generic welcome audio cache. The spoken opening is persisted as an agent transcript message using the existing controller. Its LLM usage is tracked normally. Existing campaign callback-memory openings remain a fallback when new conversation context is unavailable; scheduling is still Task 9.

Run `npm run verify:directional-conversation-openings`, the dynamic prompt suite, Agent-Initiates/welcome suites, runtime and RAG regressions. Local fixtures validate routing, limits and controller behavior. Actual provider timing, phrasing and identity handling need staging calls before release. No new `.env` values are required.
